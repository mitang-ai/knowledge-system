# 沉淀 v4.2 · 产品与设计说明

## 1. 重新设计的判断

原系统已经具备很好的起点：快速记录不强制标题，多主题关联不复制正文，留言可以保留认知变化，导出保留完整结构。交付包还有数据库 DDL、RLS、托管认证与飞书增量脚本，不能把它误判为“只有前端、完全没有后端”。缺少的是长期积累的产品组织方式与管理界面。

产品的核心路径是“写灵感 → 关联主题 → 回看”。标题和分类不阻挡即时输入；收藏资料、复杂状态与管理操作放在需要时再展开的层次中。公开代码不含个人内容、署名资料或迁移样本。

新版将最短输入路径保留，同时建立六步闭环：

**捕捉 → 整理 → 连接 → 更新理解 → 提炼经验 → 回顾与复用**。

“长期”不是让内容永远躺在数据库里。每条记录需要有出处、有可理解的上下文、有演变痕迹、有重新遇见它的机会，也能在离开平台时完整带走。

## 2. 三个层次的产品

### 个人知识空间

每个用户默认拥有自己的私有空间。个人书桌是主入口：记录框在最显眼的位置，最近更新以表格呈现在记录框下方，回顾、常用主题与当前理解放在旁侧。系统不用标题或分类挡住输入；没有关联到有效主题的内容进入收件箱。

个人资料、草稿、排版偏好、回顾计划和备份按用户隔离。即使加入团队，个人记录也不会因此向成员开放。收藏、资料、经验采用同一份内容对象，以类型与视图组织；星标只表达“需要放在手边”，不复制内容。

### 团队知识空间

团队空间与个人空间明确切换。一条内容有确定的空间归属，不能通过篡改客户端把私有主题关联到另一个团队。团队成员共同阅读、沉淀方法与补充观点，同时保留作者身份与原始来源。

当前实现支持团队创建、说明、成员列表、角色、有效期 7 天且单次使用的邀请码，以及成员移除。所有者维护成员权限；管理员可以邀请编辑或只读成员；编辑成员记录自己的内容、发表补充；只读成员只能阅读。正文由原作者修改，管理员合并主题只调整组织关系，不因此获得修改每个人正文的权力。

后续的“正式团队知识”需要与工作中的记录区分：建议新增“草稿 → 评审 → 已发布 → 待更新 → 已归档”的文档生命周期，并为操作流程指定维护人、适用范围和下次审查时间。多人同时写同一篇正式文档时，需要版本冲突提示或协同编辑，这不是当前本地版本假装已实现的能力。

### 面向更多 C 端用户的平台

产品入口应继续保持个人化，平台运营功能不混入普通用户的书桌。平台管理员维护账号状态、空间元信息、配额、服务运行情况与工单；不能为了运营方便，把所有私有正文做成可随意翻阅的内容列表。

当前交付版已有独立账号与服务端隔离，平台所有者可查看账号、空间、内容对象和备份数量，并停用、恢复账号。公开服务还需验证邮箱、找回密码、认证限流、设备/会话管理、数据删除申请与下载任务、配额、队列和监控。付费、公开社区、自动 AI 整理不进入第一版，避免改变知识管理的核心方向。

## 4. 后台管理系统是否需要

**需要，但分成知识治理、团队管理、平台管理三层。**

个人知识管理的后台重点是维护知识，不是维护一排空泛图表：待归类内容、主题说明、完全重复的正文、缺失附件、归档、回收站和可恢复备份。每个问题能跳转到对应记录进行处理。

团队管理只在团队空间出现，处理邀请和成员权限。平台管理只给实例的管理者展示账号状态和空间元信息。这样既能满足你当前的个人使用，也为团队与 C 端增长留出边界，而不用每个个人用户面对一套繁重的企业后台。

完全重复检测仅比较去除空白后的正文，结果必须人工确认；不声称能识别语义重复，也不会自动删除。主题合并在服务端事务中完成，保留关联变更的版本、原文与作者；原主题移入回收站。主题删除不删除正文，原关联保留，可恢复；引用失效的记录会进入待整理视图。

## 5. 记录、理解与经验

记录保存当时的原话；补充保存后来发生的变化；“当前理解”明确指出现在最认可的解释。设定当前理解时追加历史，不覆盖之前的补充。正文编辑也保留旧版本，避免过去的上下文无痕消失。

进展回答“做到哪里”，当前理解回答“现在怎么想”，两者可以同时存在。引用保存被讨论的片段，使后续补充不脱离上下文。主题的“补充与进展”只是聚合视图，不复制留言成新帖。

经验是值得下一次复用的内容。收录为经验保留 ID、原文、主题、来源和留言，并追加类型变更的版本。经验模板提示适用场景、做法、边界；验证状态为“需要再确认 / 我认同 / 我尝试过 / 暂时采用”。建议未来补充验证来源、适用日期、失效条件和真实应用案例，而不是把“经验数量”作为主要成功指标。

## 6. 回顾设计

原系统依靠本机打开时间和短期顺延，跨设备一致性较弱，也容易让“浏览过”误代替“理解过”。新版使用明确的回顾动作，回顾计划保存到内容记录中，不依赖某台设备的本地浏览历史。

“还要想想”安排 1 天后，“逐渐理解”安排 7 天后，“已经掌握”安排 30 天后；“明天再看”只顺延，不算正式回顾。记录保留回顾次数、上次时间、下次时间和间隔。长期推荐可以扩展为“主题关联、未解决问题、待验证经验、超过维护期的团队文档”，但第一版使用可解释、可调整的简单规则。

不自动产生通知或邮件。用户主动请求提醒后，才接入后台调度、通知偏好与免打扰时段。

## 7. 视觉设计与“AI 味道”的处理

视觉参考 Apple 的清晰层级、控件一致性与可调排版，以及 Notion 的内容优先、轻边框和空间组织方式。没有复制它们的品牌、图标或专有字体。

本次环境仅开放包管理网络，Apple、Notion、搜索引擎访问被策略拒绝。因此没有把未读取的网页称为“研究结果”。以下是可继续复核的官方参考入口，设计取舍来自已有的设计知识与对这个系统实际内容的判断：

- Apple Human Interface Guidelines / Typography：<https://developer.apple.com/design/human-interface-guidelines/typography>
- Notion / Customize and style your content：<https://www.notion.com/help/customize-and-style-your-content>

避免“AI 味道”不是机械禁止某一种颜色，而是让设计决定有具体理由：

1. 用知识内容而非营销式标语占据主要空间。标题和摘要来自真实记录。
2. 浅色使用纯白、浅灰与黑色；深色使用中性炭灰与浅色文字。主要操作和选中状态依靠明暗对比，减少装饰性颜色。
3. 知识列表使用标题、主题、更新时间组成的表格，团队列表补充作者；主题和字体选择使用适量卡片，回顾采用文字摘录，管理采用任务行。
4. 图标统一线宽与尺寸，表达功能，不用表情符号或装饰性“AI 魔法”按钮。
5. 借助细线、留白、文字级别和对齐产生层次。主题封面使用低饱和几何线条，不使用无关库存图片。
6. 每个按钮都接入具体行为；未接入的飞书显示“待对接”，本地数据不伪称云端同步。
7. 为空状态、长标题、真实中文、多附件、手机宽度和大字号设计，避免只做漂亮的首页截图。

Logo 使用为此项目设计的抽象符号「归点」：独立方点表示刚被捕捉的想法，连续的弯折轮廓表示连接与逐层沉淀。避开通用书本、灯泡和脑形图标，保留一个可直接识别的整体轮廓。单色正稿、反白稿和应用图标来自同一 SVG 路径，小尺寸不依赖文字或细线表达含义。

阅读页不把无标题正文截取后重复放大为标题；保留轻量的“添加标题”入口，正文保持完整，标题仍可留空。

## 8. 字体与排版系统

十种字体实际随项目提供，保留原 SIL Open Font License 授权，来源信息见 `public/fonts/manifest.json`。中文字体采用分片 WOFF2，按需要加载；选择字体即可在阅读区域实时生效，不依赖用户本机恰好安装。

| 思源宋体 / Noto Serif SC | 阅读、长文 | 原生中文 |
| 霞鹜文楷 / LXGW WenKai TC | 温润的个人札记 | 含简体的 TC 版本 |
| 霞鹜文楷等宽 | 整齐的笔记 | 含简体的 TC 版本 |
| 站酷小薇体 | 中文标题、短文 | 原生中文 |
| 站酷庆科黄油体 | 轻松的短记录 | 原生中文，长文谨慎使用 |
| Inter | 中英混排的简洁文字 | 中文回退到思源黑体 |
| IBM Plex Sans | 人文风格的拉丁文字 | 中文回退到思源黑体 |
| Source Sans 3 | 通透的拉丁正文 | 中文回退到思源黑体 |

正文 13–28px、界面 13–18px、页面标题 26–42px、行距 1.4–2.4、阅读宽度 520–900px 可通过滑块或数字输入调整。移动端自动限制阅读宽度，避免横向滚动。字号控制与字体预览同时可用；字体名称只是控件文字，预览文字使用对应真实字体。

另有浅色/深色/跟随系统、舒展/紧凑、减少动效。右上角常驻深浅色开关，切换保留当前字体、字号等偏好；手机端、登录页与阅读弹窗同样可使用。视觉焦点可见，浮层支持 Esc、键盘焦点限制与关闭后返回焦点，尊重系统减少动态效果设置。

## 10. 数据架构与公开服务扩展

当前架构为 React / TypeScript / Vite，Python 标准库 API，SQLite WAL，附件存本地目录。原始字段保留在结构化 JSON 中，独立索引包含 ID、owner、kind。身份来自服务端会话，不接受前端指定作者。主题合并、恢复和导入使用数据库事务。账号密码使用 scrypt，会话 token 只存哈希，Cookie 为 HttpOnly、SameSite=Strict；开发预览的允许来源是明确的本地地址。

当前为评审和本地使用采用全量加载**可访问数据**，并在前端筛选。公开 C 端版本应先迁移成以下模型，而不是等到数据量膨胀后继续加前端过滤：

- `users`、`identities`、`sessions`：生产认证、邮箱校验、设备与会话。
- `workspaces`、`memberships`、`invitations`：个人/团队空间、角色、单次邀请、成员状态。
- `entries`：空间、作者、类型、标题、正文、生命周期、revision、时间、软删除。
- `topics`、`entry_topics`：多对多关系，避免长期依赖 JSON 数组做索引。
- `replies`、`understanding_history`：上下文、引用、进展、当前理解。
- `entry_versions`：不可覆盖的正文与关系变更历史。
- `attachments`：对象存储路径、哈希、mime、大小、归属与处理状态。
- `review_states`：按用户的复习计划。当前版本已经将回顾状态独立存储；团队同一条知识允许每个成员有自己的回顾周期，只读成员也可以回顾，不会改变作者正文。
- `export_jobs`、`backup_jobs`、`audit_events`：异步导出、对象清单、异地备份、敏感操作记录。

所有带内容的表以 `workspace_id` 为必填字段，在服务端查询和数据库策略中验证成员权限。PostgreSQL 下使用 RLS 作为第二层边界；分页、检索、全文索引和排序都进入服务端。标题和正文使用 revision / ETag 做乐观锁，冲突时保留双方版本；真正的协作编辑再引入 CRDT。

图片与文件进入私有对象存储，先验证上传大小、类型与内容，再生成短期签名链接。导出任务保存文件哈希与缺失清单。正式备份采用服务端调度和异地存储，定期测试恢复；账号删除与团队归档需要明确的保留周期。

团队正式知识增加负责人、审查日期、发布状态和引用关系；C 端增加公开链接的显式开关、可撤销令牌、隐私预览与滥用处理。当前不会替用户发布知识，也不会将“所有登录用户可读全部正文”作为共享默认值。

## 11. 交付范围与后续优先级

已实现的功能见 README 与验证记录。以下是生产化顺序，不应冒充当前已接入：

1. **上线基础**：生产认证、邮箱找回与验证、HTTPS Cookie、登录限流、环境配置、托管数据库和对象存储。
2. **团队可靠性**：文档 revision 冲突提示、团队发布/评审/维护人、操作审计。
3. **增长能力**：服务端分页与检索、导出队列、配额、异地备份与恢复演练、账户删除与数据下载。
4. **可选增强**：飞书连接、浏览器剪藏、公开只读分享、移动端离线同步、显式启用的内容建议。

更适合长期衡量的指标是：能否找到过去的记录、收件箱是否能持续清理、经验是否被复用、理解是否得到更新、完整导出是否能恢复。活跃时间、记录总数、卡片总数本身不等于知识质量。
